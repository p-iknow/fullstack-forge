# Auth Domain UI

## §7 UX 정책 (auth)

### 공통

- 세션 만료 시 자동 로그인 페이지 이동 + 안내 토스트
- 로그인 실패 사유는 보안 범위 내 일반화된 문구 사용

### Store surface 전용

- OAuth callback 중 로딩 상태 표시

## Store 로그인 화면

- 로그인 화면은 3가지 진입점 명확 노출: Email / Google / Kakao
- 이메일 입력 + 비밀번호 입력 + 로그인 버튼
- 소셜 로그인 버튼 (Google, Kakao)
- "회원가입" 링크
- "비밀번호 찾기" 링크

## Store 회원가입 화면

- 입력 항목: 이메일, 비밀번호, 비밀번호 확인
- 비밀번호 정책(최소 8자)을 화면에서 즉시 안내
- 가입 성공 시 추가 인증 단계 없이 로그인 완료 상태로 이동

## Admin 로그인 화면

- **이메일 로그인만 제공** (OAuth 버튼 없음)
- 이메일 입력 + 비밀번호 입력 + 로그인 버튼
- "비밀번호 찾기" 링크
- **회원가입 링크 없음** (운영자 계정은 관리자가 생성)
- `customer` 역할로 로그인 시도 시: "이 계정으로는 접근할 수 없습니다" 안내

> Admin 로그인 화면은 store보다 간결하다. 소셜 로그인과 자가 가입 경로가 없으므로
> 공격 면(attack surface)이 줄어들고 관리자 전용 접근이라는 인식을 명확히 한다.

## 비밀번호 재설정 화면 (store/admin 공통)

- 1단계: 계정 이메일 입력 후 재설정 요청
- 2단계: 새 비밀번호/확인 입력 후 재설정 확정
- 재설정 완료 시 기존 세션 만료 안내 후 로그인 화면으로 이동

## 접근 정책

### Store surface

- `customer` 역할: store 접근 허용
- store 세션(`qc_access`)으로만 store API 접근 가능

### Admin surface

- `operator` 역할: admin 접근 (운영 업무)
- `admin` 역할: admin 접근 + 운영/정책 변경
- admin 화면/API는 `operator|admin`만 허용
- `customer` 역할 로그인 시도 시 `403 auth_insufficient_role`
- store 세션(`qc_access`)으로 admin API 호출 시 `403` (surface 불일치)
