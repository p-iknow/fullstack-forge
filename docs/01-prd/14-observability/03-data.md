# Observability Domain Data

이 문서는 observability 도메인의 데이터 구조를 개념 수준으로 정의한다.
컬럼 타입/인덱스 상세는 포함하지 않는다.

## 1) 메트릭 저장 엔터티(있는 경우)

- 관측 스택 기본 저장소는 Prometheus TSDB를 사용한다.
- 애플리케이션 내부에 별도 메트릭 스냅샷 저장이 필요한 경우에만 보조 엔터티를 둔다.
- 보조 엔터티는 운영 리포트/감사 보존 목적이며 실시간 경보의 단일 기준은 Prometheus로 유지한다.

## 2) 핵심 메트릭 개념

- 큐 상태: queue depth, DLQ 메시지 수
- 처리량/실패: worker 처리 총량, 실패 총량
- 지연: 이벤트 처리 지연, API 지연, 문의 1차 응답 지연
- 운영자 활동: 리뷰 신고 처리량, redrive 수행 이력

## 3) 감사 로그 구조

- 모든 이벤트 처리 로그에 `traceId`, `eventId`, `consumer` 기록
- 주문 단위 추적 가능해야 함(end-to-end)
- redrive 수행 기록은 별도 감사 로그 필수

## 4) 감사 로그 기록 단위

- 공통 식별: traceId, eventId, 주문 식별자(있는 경우)
- 처리 문맥: consumer, 처리 결과, 실패 코드, 수행 시각
- 운영 문맥: redrive 실행자, 실행 사유, 실행 결과

## 5) 데이터 정합성 원칙

- 대시보드 지표와 감사 로그는 동일 traceId로 교차 검증 가능해야 한다.
- DLQ/복구 관련 운영 지표는 감사 로그와 일치해야 한다.
- KPI 측정에 사용되는 집계 값은 기간/대상 기준을 명시해 재현 가능해야 한다.
- KPI 목표 정의는 [00-overview.md §3 성공 지표](../00-overview.md#3-성공-지표-kpi-7개)를 단일 기준으로 참조한다.

| ------------- | ---------------- | -------------------------------------- |
